01

Is this even a review?

apps/action/src/event.ts · inspectEvent packages/schemas/src/pull-request-event.ts · the trigger list

This runs before any client and any model — it is the first thing runAction does after parsing GITHUB_EVENT_PATH. An event that will not be reviewed has nothing to load, so asking the question first is what lets the answer "no" cost nothing.

Two outcomes, and the difference between them is the whole point of this file.

OutcomeWhenResult
Not a review Wrong event name, or an ignored action like labeled Logs review.skipped, step succeeds
Malformed Claims to be a supported pull_request event but fails the schema Throws — fails the workflow

Most workflow triggers are not reviews, so ignoring one quietly has to be a success. A payload that should have parsed and didn't is a bug worth failing over.

A reviewable event yields the target, the base SHA, and whether the pull request came from a fork. Only now does boot begin.

02

Boot — the Action entrypoint

apps/action/src/index.ts

runEntrypoint() runs at import time, but returns immediately unless GITHUB_ACTIONS === "true" — so importing the module in a test does no work and needs no configuration.

runAction then builds each dependency in a deliberate order: the GitHub client first, then the model client, so a missing token or key fails the step before any review work begins.

StepFunctionFails the run?
GitHub clientcreateTokenClientYes missing token

Tracing starts before the prompt fetch, so the fetch's own spans are captured; prompts resolve before anything that consumes them is built.

createLanguageModel is the only place a provider is chosen. packages/ai/src/model.ts holds the registry — openai (the default, gpt-5.6-luna) and anthropic (claude-sonnet-5) — and every model call in the run goes through generateText from the AI SDK against whichever it built.

03

Load the pull request

packages/reviewer/src/review-pull-request.ts packages/github/src/client.ts · the interface

Three GitHub reads, concurrently. This is the only place the review context is built.

client.ts is the interface and nothing else; the Octokit implementation behind it lives in app.ts, which paginates the file and comment lists and Zod-parses every response before it becomes a type the rest of the run trusts.

One source of truth changedFiles is read by the agent and by validate. Because both read the same list, validation can never check findings against a different set of files than the one the agent actually reviewed.

The pipeline

packages/reviewer/src/review-pipeline.ts

One agent runs, then its candidates are validated in sequence. If the agent fails, the pipeline throws and the run fails.

4a · The agent

packages/ai/src/agents/runtime.ts · createReviewAgent packages/ai/src/agents/definition.ts · what an agent is packages/ai/src/agents/output.ts · parsing the answer

The agent is an AgentDefinition — role, focus text and category — run by one shared runtime: the loop, the eight tools, the injection hardening and the output contract all live there.

The loop itself is the AI SDK's. The runtime's job is the boundary around it: cap the turns, notice when the cap was hit, and refuse anything that is not the agent's own category.

Hitting the cap is a failure, not a truncated answer: an agent still mid-tool-call has not reported, and its silence must not be read as "found nothing". The token counter lives outside the try, so an agent that dies mid-loop still reports what it spent.

Each turn asks for two things to be cached. A breakpoint on the system message pins the prefix, tools included, so later turns read it rather than paying for it again; a call-level one follows the growing conversation tail, so turn two reads turn one's opening message and tool results from cache. The three input counters are logged separately on agent.completed for exactly this reason — a cache that stops hitting raises the bill and changes nothing else.

extractAgentOutput takes the outermost JSON object out of the final message and Zod-validates it; output it cannot parse fails the agent, which fails the run. After that the runtime filters findings down to the agent's own category. Cross-category leaks are dropped, never re-stamped — re-stamping would fabricate a claim the model never made, while dropping keeps category provenance deterministic.

The eight tools

packages/ai/src/agents/tools.ts

These are the only tools the agent ever gets. There is no write, comment, approve, merge, or execute tool anywhere in the package — so the restriction holds by construction rather than by prompt.

ToolReads
get_pull_requestTitle, description, author, branches, SHAs
list_changed_filesThe changed-file list
get_diffOne changed file's patch by path; with no path, the changed-file list with patch sizes
get_fileOne file at the head SHA — the proposed state
get_base_fileOne file at the base SHA — before this PR
search_repositoryCode search with matching snippets and the repository-wide total, always scoped to this repository
find_referencesFiles importing one file, or one of its exported names, resolved from the repository index at the base SHA
find_co_changed_filesFiles edited in the same recent commits as one file — correlation, not dependency

The first three answer from what the run already loaded, so they cost no GitHub call. search_repository and find_co_changed_files read the default branch — one through GitHub's code search index, the other through commit history. Their results do not reflect this pull request and their snippets carry no line numbers, so a claim about a changed file still needs get_file.

find_references is different: it answers from the repository index this review built at the pull request's base commit, so what it returns is the import statements themselves rather than a text search. It gives every file importing a path with the line each import sits on, or — given a name — only the files importing that export, with default and namespace (*) imports marked. At most 50 files come back, alongside the true total. Every result carries an index header naming the commit, whether the index is truncated, which languages were parsed and how much of each one's internal imports were placed, so an agent can tell an empty answer from an unindexed one; a path the pull request added, or one the index does not hold, comes back as known: false with the reason rather than as a file that does not exist. With no index for the review it returns one line saying so, and the agent falls back to the other tools.

The index itself is built once, in memory, from one archive request at the base SHA, and thrown away when the review ends — nothing is stored. It parses TypeScript and JavaScript only, and resolves the way the repository's own tooling does, in one order: a relative path (extensionless, through index files, a written .js to the .ts or .tsx behind it), a # import map from the nearest package.json, a tsconfig.json paths alias with its extends chain followed, then a workspace package name through that package's exports map. Workspace packages come from pnpm-workspace.yaml or package.json workspaces; a third-party package is kept unresolved rather than guessed at, and a malformed manifest costs that one file's contribution rather than the build. Every other language is seen for its role and its tests, and reported as not indexed.

What the resolver could not place is not hidden. Each indexed language carries a resolution rate — the share of the imports that are not third-party which landed on a real file — and that rate travels in every find_references header. A repository whose alias scheme this resolver does not understand reads as a low rate rather than as a suspiciously short list of importers. The opening message also gains a <repository> block: every workspace package with its root, the indexed commit, and the same per-language summary, so an agent has bearings in a monorepo it has never seen.

Every input is Zod-validated by the tool's own inputSchema before it touches the GitHub client: paths may not be absolute or contain traversal segments, and a search may not carry repo:, org: or user: qualifiers — the client adds the only scope there is. A failing execute becomes an error result the model reads and continues from, so a bad tool call costs a step rather than the run.

Every result is truncated at 50k characters, so one enormous file cannot spend the whole context.

4b · validate — the trust boundary

packages/reviewer/src/validate-findings.ts

Seven deterministic steps, in this order. No I/O, no model, no mutation of its inputs.

  1. Schema validity — reviewFindingSchema (Zod)
  2. The category is the agent's own — general; the schema cannot check this, since the category is a free slug
  3. The file exists among the PR's changed files
  4. The line is an added line in that file's diff, when a line is given
  5. Confidence ≥ 0.7 — CONFIDENCE_THRESHOLD
  6. Duplicate removal — the strongest of each group survives
  7. Cap at 10 — MAX_FINDINGS, keeping the strongest

"Strongest" is fully deterministic: severity rank, then confidence descending, then input order. Dedup runs before the cap, so duplicates cannot consume cap slots and leave the review short.

This is where bad output dies A fabricated file path, an invented line number, or a padded confidence score is dropped here — regardless of how confident the model sounded when it proposed it.

4e · verifyPatches — proving a fix

packages/reviewer/src/validate-patches.ts

A finding may carry a patch: a replacement for a line range, quoted alongside the expected text it replaces. The quote is the whole mechanism. The file is re-read at the head commit and compared character for character — there is no fuzzy match and no apply-with-offset.

  1. The range's current text equals expected — byte for byte, at the head commit
  2. The range touches the diff — the agent may not rewrite a part of the file this PR never changed
  3. No two kept patches overlap in one file
  4. Cap at 5 files and 200 lines — MAX_PATCHED_FILES, MAX_PATCHED_LINES
A failed patch costs the fix, never the finding Every rejection strips only the patch. The finding is published as it would have been without one, so a miscounted line number never silences a real problem.

06

Publish

packages/reviewer/src/publish-review.ts · deliverReview apps/action/src/summary.ts · createFallbackPublisher

Inline comments go first, and the check run annotates only what no comment carries — including comments an earlier commit already left. Annotations are the fallback surface, not a duplicate.

Then the check run. On a 403 or 404, write the same rendered review to the workflow job summary and exit cleanly — that is the fork case, where GitHub hands the workflow a read-only token.

commentsMeaningAnnotations
"posted"Fresh comments landed on this commitNo
"already-posted"Every finding was commented on an earlier commitNo
"unavailable"The token cannot post comments (fork)Yes
"nothing-to-post"No findingsN/A

Everything else propagates and fails the step: 401 is a bad token, 429 is rate limiting, 5xx is an outage, and an error with no status at all is a network failure. None of those may masquerade as a delivered review.

The cost of being wrong is asymmetric in both directions, which is why the rule is this narrow. Too permissive, and a real GitHub outage renders as a clean review nobody investigates. Too strict, and every fork pull request fails CI.

Lifecycle log events

Every event of one review carries repository, pullRequestNumber, and headSha — so an operator can answer "what happened to the review for PR N?" from the logs alone.

review.model_selected
review.started
  → review.loaded
    → agent.started  → agent.completed / agent.failed
    → findings.validated
    → patches.verified
  → review.fixes.applied / .degraded / .disabled
  → review.comments.published / .degraded / .list_failed
  → review.published / review.published.degraded / review.failed

agent.completed and agent.failed both carry four token counters, not two: where a provider caches, the three input counters bill differently.

Run it yourself

evals/src/run-fixture-review.ts evals/fixtures/

The whole path above runs against a fixture repository on your own machine. A fixture is a directory: repo/ is the tree at the head commit, base/ holds the previous contents of the modified files, and a manifest names the pull request. The harness builds the diff from those two trees and serves every tool call from memory, so nothing reaches GitHub — and the two publish steps are the only things replaced.

The fixtures are chosen to fail in different directions. Most plant a known problem for the agent to find; clean-pagination is correct code that must produce no findings at all — the case that catches a model inventing problems to look useful.

A run asserts a finding anchored to each planted problem, no findings on the clean fixture, and a health check that the agent completed. Everything else comes from the ordinary pipeline log: agent.completed carries the duration, the four token counters and the finding count.
