  supersedeForLiveHead used to return early when the fenced supersede failed. Now it enqueues whatever it read even after the fence has rejected it. A worker whose lease lapsed is usually one that stalled, often between `getPullRequest` and this transaction. Here is the sequence: the stale worker reads live head B, the author then pushes C, and the webhook enqueues C, which starts running. The stale worker wakes up, its supersede is a no-op, and `headJobSucceededOrActive(B)` is false because B was superseded by C. `enqueueReviewJob(B)` then inserts B and, because its head differs, marks C's running job `superseded`. C's worker can no longer settle, so its review is thrown away. The job for B later sees live head C and enqueues C again, so this heals itself, but it wastes a full review run and its tokens. The old fence-gated early return kept a stale worker from acting on old state.
  Fix: When the fence fails, enqueue only if the pull request has no active or succeeded job at all. Another option is to re-read the live head inside the transaction window. Either way, a fenced-out worker should never supersede a job for a head other than its own.
